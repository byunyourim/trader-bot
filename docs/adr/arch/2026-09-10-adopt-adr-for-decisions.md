# ADR로 설계 의사결정을 기록한다

## Context
AI와 대화하며 설계·구현을 진행하는데, 그 과정에서 내린 결정과 근거가 대화가 끝나면
휘발된다. 나중에 다시 보거나 이어서 작업할 때 "무엇을 왜 그렇게 정했는지"를 복원할
수 없어 같은 논의를 반복하게 된다. AI에 전부 맡기지 않고 확장성 있는 설계를 사람이
주도하려면, 의사결정 과정이 일관된 형태로 남아야 한다.

## Options
1. **ADR 문서 (영역별 폴더 + 날짜 프리픽스, immutable + supersede)** — 결정 1건 = 파일 1개.
   업계 표준이고 git으로 버전·검색 가능. 결정이 바뀌면 새 ADR로 대체해 히스토리 보존.
   단점: 결정마다 파일이 늘어나고 명시 작성 습관이 필요.
2. **단일 DECISIONS.md 로그** — 파일 하나에 시간순 누적. 가볍지만 길어지면 무겁고
   영역 구분·supersede 추적이 어렵다.
3. **세션별 작업 로그** — 날짜별 세션 기록. 재개엔 좋지만 "결정" 단위 검색·대체 관리가 약함.

## Decision
옵션 1(ADR)을 채택한다. 이 프로젝트는 이미 DDD 컨텍스트(market/order/account) + infra로
나뉘어 있어 영역별 하위 폴더가 구조와 1:1로 맞는다. 파일명은 날짜 프리픽스로 카운터
관리를 없애고 시간순 정렬을 얻는다. ADR은 수정하지 않고 새 ADR로 대체(supersede)해
"왜 생각이 바뀌었는지"까지 보존한다. 작성은 자동화하지 않고 `/adr` 슬래시 커맨드로
명시 호출한다(통제력·저노이즈). 전용 에이전트는 지금은 만들지 않는다.

## Consequences
- 설계 결정과 근거가 영역별로 남아, 재개·온보딩·설계 능력 향상에 직접 도움.
- 결정마다 `/adr` 을 명시 호출하는 습관이 필요(자동 생성 아님).
- 후속: 인프라 개선은 별도 서브프로젝트로 brainstorm. planner 연동·자동 코덱스
  교차검증은 필요해지면 확장. 스펙 `docs/superpowers/specs/2026-09-10-adr-decision-recording-system-design.md`.
