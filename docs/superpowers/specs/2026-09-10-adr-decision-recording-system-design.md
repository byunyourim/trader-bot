# ADR 기반 의사결정 기록 시스템 — 설계

- 작성일: 2026-09-10
- 상태: 승인됨 (구현 대기)

## 목적

AI에 전부 맡기지 않고, 확장성 있는 설계를 사람이 주도하면서 그 의사결정 과정을
일관된 기록으로 남긴다. 나중에 다시 보거나 이어서 작업할 때 "무엇을, 왜 그렇게
정했는지"를 흐름째로 복원할 수 있게 하는 것이 목표다. 부수 효과로 설계 능력 향상을
노린다.

이 스펙의 범위는 **의사결정 기록 시스템(ADR)** 하나로 한정한다. 원래 프로젝트
목적에 있던 인프라 개선은 범위가 크므로 별도 서브프로젝트로 분리한다.

## 핵심 결정 (확정)

- 기록 형태: **ADR 문서** (결정 1건 = 파일 1개)
- 분류: **영역별 하위 디렉토리** (DDD 컨텍스트 + infra + arch)
- 파일명: **날짜 프리픽스** + 영어 슬러그
- 불변성: **immutable + supersede** (기존 ADR 수정 금지, 새 ADR로 대체)
- 생성: **명시 호출** (`/adr` 슬래시 커맨드) — 자동 생성 안 함
- 구현 범위: **슬래시 커맨드 하나**로 (전용 에이전트는 만들지 않음, 나중에 필요 시 추가)
- 코덱스: **선택적 교차검증** (중요 결정에만 두 번째 의견)
- 일관성: 템플릿을 **고정 계약**으로, 커맨드가 검증 후 저장
- 언어: **한글 본문**, 항목명·코드·기술용어·파일명 슬러그만 영어

## 디렉토리 구조

```
docs/adr/
  README.md                       # ADR 인덱스 (에이전트가 자동 갱신)
  template.md                     # 고정 계약 템플릿
  market/
  order/
  account/
  infra/
  arch/                           # 특정 컨텍스트에 안 속하는 전역 결정
```

- 번호 카운터를 관리하지 않는다. 파일명 날짜가 시간순 정렬을 제공한다.
- 파일명: `<YYYY-MM-DD>-<english-slug>.md`
  - 같은 날 같은 영역에 2건 이상이면: `<YYYY-MM-DD>-1-<slug>.md`, `-2-` …
- 여러 영역에 걸친 결정은 `arch/`에 둔다.

## ADR 템플릿 (고정 계약)

```markdown
---
status: Proposed        # Proposed | Accepted | Superseded  (이 3개만)
date: 2026-09-10
area: order              # market | order | account | infra | arch  (이 5개만)
supersedes:              # (선택) 이 결정이 대체하는 이전 ADR 경로
superseded-by:           # (선택) 이 결정을 대체한 ADR 경로
---

# <결정 제목: 동사형 한 문장, 예: 주문 멱등성을 requestId로 보장한다>

## Context
<배경·제약. 무엇을 풀려는가, 어떤 조건이 있었나.>

## Options
1. **<옵션 A>** — <트레이드오프>
2. **<옵션 B>** — <트레이드오프>
   (항상 2개 이상)

## Decision
<선택한 옵션과 근거. 다른 걸 안 고른 이유 포함.>

## Codex second opinion
<선택: 코덱스 교차검증을 돌린 경우 핵심 반론·동의 요약. 안 돌렸으면 "N/A".>

## Consequences
- <긍정적 영향>
- <감수하는 단점·리스크>
- <후속 작업 / 영향받는 코드·모듈>
```

### 일관성 강제 규칙

1. **고정 어휘**: `status`, `area`는 위 enum 값만 허용. 새 영역이 필요하면 규칙
   갱신(이 스펙 + 에이전트 지침)부터 한다.
2. **섹션 고정**: 순서·제목 고정, 임의 추가/삭제 금지. 안 쓰는 섹션은 삭제 대신 `N/A`.
3. **문장 규칙**:
   - 제목: 항상 동사형 한 문장.
   - Options: 항상 2개 이상, `**옵션명** — 트레이드오프` 형식.
   - Consequences: 항상 불릿, 긍정 → 부정 → 후속작업 순.
4. **저장 전 검증**: 누락 필드, enum 위반, 빈 섹션, 형식 위반을 체크리스트로 검사하고
   통과해야 저장한다.

## 컴포넌트

### 1. `/adr` 커맨드 (`.claude/commands/adr.md`)

이 커맨드 하나가 시스템의 전부다. 템플릿 계약·고정 어휘·검증 체크리스트를 모두
커맨드 지침 안에 담는다. 별도 에이전트는 만들지 않는다.

호출 예: `/adr` · `/adr order 주문 멱등성` · `/adr --codex`

흐름:
1. 최근 대화에서 결정 내용 추출(배경·검토한 옵션·최종 선택).
2. `area` 판별 → 대상 폴더 결정.
3. 템플릿 계약대로 초안 작성 → 검증 체크리스트 통과.
4. `docs/adr/README.md` 인덱스 갱신.
5. 기존 결정을 뒤집는 경우: 옛 ADR을 `status: Superseded` + `superseded-by`로
   갱신하고, 새 파일에 `supersedes` 링크를 넣는다. (옛 ADR 본문·파일명·날짜는
   건드리지 않는다.)
6. 파일명 슬러그는 영어, 본문 H1 제목은 한글로 작성한다.

### 2. 코덱스 선택적 교차검증

- 트리거: `/adr --codex` 또는 클로드가 "중요 설계 결정"으로 판단해 제안할 때.
- codex consult/challenge로 반론을 받아 `Codex second opinion` 섹션에 요약한다.
- 돌리지 않으면 해당 섹션은 `N/A`.

## README 인덱스 형식

`docs/adr/README.md`는 에이전트가 갱신하며, 영역별로 표를 둔다.

```
## order
| 날짜 | 결정 | 상태 |
|---|---|---|
| 2026-09-10 | 주문 멱등성을 requestId로 보장한다 | Accepted |
| 2026-09-03 | (구) 주문 멱등성을 DB 유니크 제약으로 처리 | Superseded |
```

`Superseded` 표시로 옛 결정을 한눈에 구분한다.

## 범위 밖 (별도 서브프로젝트)

- 인프라 개선: 별도 brainstorm → 스펙 → 계획 사이클로 진행.
- ADR 작성 전용 에이전트: 지금은 슬래시 커맨드만. planner 등 다른 에이전트가 설계
  끝에 자동으로 ADR 초안을 호출하는 연동이 필요해지면 그때 추가.
- ADR 자동 생성/자동 코덱스 교차검증: 지금은 명시 호출·선택적만. 필요해지면 확장.
